# EzDSH 环境问题处理：用户流程与改进设计

日期：2026-09-13。初次核查基线：HEAD `0cf4845`。本文记录整体设计与验收方案；后续已实施第 0 步的安装错误归因与恢复文案改进、第 1C 步的目录/命令诊断和手动修复入口、安全模式持续使用与重启保留，以及第 1B 步首批的恢复前预检和还原后启动重试，执行记录见文末。其余阶段仍是规划；完整恢复编排和跨平台发行验证尚未完成。工作区已有的 Workflow、package.json、恢复页 CSS 等改动不属于本次工作。

## 1. 要解决的问题

用户需要知道的是：还能不能继续使用、接下来点哪里、操作会不会影响自己的数据。用户不应先学会区分 Runtime、profile、PATH、安全模式和隔离模式，才能恢复应用。

目标流程：应用自动进行有时限的检查；能确定且影响很小的问题由应用处理；需要用户决定时只突出一个推荐动作；每次操作后验证对应能力；仍未恢复时保留检查结果并给出下一步。

首屏固定回答三件事：**哪里不能用、目前知道什么、下一步做什么**。数据影响放在动作旁边。技术细节默认折叠，始终可查看；高级入口保持可达。

不把所有错误叫作“环境损坏”。模型服务拒绝访问、商店包不存在、外部项目缺命令、应用自身缺文件，需要不同处理。无法确定原因时明确显示“尚未确定原因”，不能将候选插件或历史日志当作结论。

## 3. 必须先修正的体验基础

### A. 应用打不开时，恢复入口也可能打不开

`src/main/index.ts:2670` 先创建数据目录、初始化工作区服务，随后才创建主窗口。初始化失败在 `:2726` 弹出原始错误后退出。现有 RecoveryPanel 不能覆盖这条路径。

改进：先保证一个不依赖工作区服务的最小应用外壳。失败时保留原数据位置，显示“重新检查”和针对当前证据的下一步。找不到外置卷时提示重新连接并检查；目录权限问题提供选择有权限位置的流程。位置变更需要验证是否包含原有数据，并单独确认迁移或切换。

失败外壳使用内存状态和可写的应用级诊断位置，不能把日志、IPC 或页面加载重新绑定到出错的数据目录。磁盘满时允许只显示并复制脱敏摘要。已有工作区不可访问时不能静默新建空工作区。

还要前移到工作区指针读取：`src/main/state/workspace-service.ts:63` 对配置损坏、读取失败和无效 root 都回退默认目录，随后初始化可能创建默认环境。应区分首次没有配置与已有配置读取/解析失败；后者保留错误并进入故障外壳，不静默 fallback。否则用户仍可能误以为原数据消失。

这个外壳只能覆盖 Electron 进程已经启动的情况。系统在进程启动前阻止运行、平台/架构不匹配、应用主体无法加载时，需要安装器和下载/帮助页提供同样简短的对应路径：识别实际系统提示，选择匹配的正式安装包，保留原数据位置。发布验收核查真实系统提示与签名状态，不把关闭系统保护、关闭杀毒或终端绕过作为通用处理方式。

### B. 当前成功条件太早

`src/main/runtime/health-check.ts:42` 以 HTTP 成功响应作为 Runtime 健康；带启动 token 的 URL 会改为探测公开静态资源。`src/main/index.ts:437` 随即完成待确认的变更事务。然而 Web 插件失败由 `src/main/runtime/runtime-view-controller.ts:132` 稍后报告。

最强反例：静态资源返回 200，前端插件加载失败。后台先清除了变更事务，用户随后才看到故障。

改进：区分服务已响应、当前启动对应的界面已就绪、受影响能力验证通过。使用与启动实例绑定的明确就绪信号，不把“没有看到错误 DOM”当成成功。保留当前启动的事务关联，直到验证通过；迟到的旧事件不得关闭新故障。恢复只做不产生业务写入的能力检查，不为验收自动发送消息、运行用户工作流或调用付费模型。

### C. 恢复备份后的服务没有完整重建

普通备份恢复 IPC 经 `RecoveryRestoreCoordinator` 调用 `stopApplicationComponents()`，停止 Workflow、外部服务、渠道、External API 和移动服务。Renderer 随后请求 Runtime 启动；该动作仍不等于重新构建全部服务实例。另有插件回滚的独立路径，只停 Runtime 却还原完整数据，尚未统一。

第 1B 步首批已将选择解析、摘要校验和归档目录读取放到停止组件之前，并固定预检确定的备份名称。设置页还原后只在 Runtime 返回 ready 时显示启动成功；启动失败保留已经还原的结果，用户可只重试启动。还原状态由 App 持有，设置页卸载后继续显示反馈；切换工作区时清除旧状态并忽略迟到结果。初次自动启动只请求一次，恢复进行中或等待重试时不再自动启动。

后续改进：所有完整还原，包括“回滚插件变更”，统一走 Main 编排：检查选定快照 → 阻止新写入并停止相关服务 → 保存当前状态 → 还原 → 重新读取配置和构建服务 → 启动并验证。停止前可发现的校验失败不应打断仍可工作的应用。中途失败保留故障步骤、恢复前备份和重试入口；不能仅因还原 Promise 成功或当前 Runtime 健康检查通过，就显示所有能力均已恢复。

快照还原包含历史运行记录。重新初始化 Workflow 等服务时先恢复到受控状态，不能未经核验就重放旧队列或重复外部写入。旧内存实例不能继续持有已经被还原的数据。

还原预览还须检查可用空间、写权限和数据格式兼容性，并在实际执行时重新验证所选归档。当前 manifest 解析与 preflight 只提供部分格式检查和版本展示，没有证明任意新旧版本之间都可读；不能承诺任意备份都能恢复可用。

当前 dry-run 只读取 tar 目录，未执行完整预解压检查；必需组件、符号链接与实际写入条件仍可能在停止服务后才失败。同名归档在预检之后被修改也可能导致后续校验失败。App 保存的还原反馈未落盘，切换工作区时清除反馈不会撤销已发出的 Main 操作；窗口重载、应用退出和完整恢复中断处理仍属于后续编排。

### D. 初次核查发现的误导归因

- 初次核查时，外部服务的有效命令配不存在的 cwd 会得到 `ENOENT`，并被解释为“程序不存在”。第 1C 步现已先检查目录，再根据该次启动的实际上下文区分命令问题；现存脚本缺解释器、损坏符号链接等不再被推断为未安装命令。
- 初次核查时，`ERR_PNPM_FETCH_401/403` 被 `install-diagnostics.ts` 的通用网络规则抢先匹配；`spawn git ENOENT` 被解释成内置包管理器缺失，均已直接复现。第 0 步已修正这两类归因。
- 初次核查时，恢复页写着“删除冲突的插件”，但列出的只是已安装插件。第 0 步已改为“查看已安装插件”，并说明列表不代表故障原因。安全模式同时跳过多类扩展，成功也不足以归因于某个插件。

改进：结构化错误码、实际失败步骤和当前目标优先；字符串匹配只能补充线索。检查目录成功后再检查命令；版本明确不兼容与一般加载失败分开；没有明确证据时保留未知。对下载源 403 应说“来源拒绝访问”，不能直接推断用户登录过期。

## 4. 用户场景与最短处理路径

表中“当前事实”来自本轮代码或定向复现；“待验证”是发行验收场景，不表示用户当前机器已经出现。

| 用户看到的症状 | 应用先检查什么 | 推荐动作与结果 | 边界 / 当前依据 |
| --- | --- | --- | --- |
| 安装器或系统直接提示无法打开 | 实际系统提示、平台/架构、安装包完整性、签名状态 | 安装器或帮助页给出匹配安装包和对应系统处理入口 | 应用进程未启动时无法在应用内自修；正式发行环境待验证 |
| 双击后打不开 | 启动步骤、应用组件、数据位置可访问性 | 留在最小故障页；按证据重新检查位置或应用完整性 | 当前存在窗口前初始化失败路径；打包故障注入待验证 |
| 数据像突然不见了 | 当前数据位置、原位置、挂载卷、当前是否隔离模式 | 找回原数据位置；隔离模式清楚显示“这里不显示原会话” | 不以空列表证明数据丢失；不自动建新环境 |
| 启动很久或失败 | 当前实例进程、端口、HTTP、页面就绪，各阶段时限 | 显示实际步骤；临时失败最多自动重试一次，失败后停止重复 | 端口自动处理已有；统一阶段与重试预算待实现 |
| 更新或装插件后打不开 | 待确认事务、兼容性、当前 profile、当前错误 | 明确不兼容则展示已停用结果；否则推荐尝试安全模式 | 回到备份是独立选择，不能默认回退历史会话 |
| 只有页面白屏 | 导航结果、当前认证、Web 就绪、加载错误 | 重建当前页面连接并验证；仍失败保留报告 | cookie 定向清理已有；HTTP 200 不代表页面正常 |
| 安装插件一直转圈 | 下载头、响应体、安装进程、安装后验证 | 有阶段、有时限、可取消；取消后保留诊断 | downloader `:113-124` 未覆盖完整 body 时限；进程取消待补齐 |
| 代理测试成功但安装失败 | 本次目标及本次操作实际使用的网络配置 | 在错误处“检查此连接”，区分代理与目标响应 | 当前代理文案明确仅覆盖 Runtime，并非已实现全局代理 |
| 模型连接失败 | 目标地址、DNS/TLS、认证、限流、服务响应 | 只在对应证据下显示修改连接、更新凭证或稍后再试 | 模型路径专项覆盖待验证；不能用重装应用解决上游拒绝 |
| 外部服务在终端能运行 | 先检查 cwd，再检查该命令和必要环境 | 已提供目录选择与对应字段编辑，明确保存后重试 | Finder PATH 回退已有；Windows 与正式发行启动仍待实测；不修改 shell 文件 |
| 提示缺 Node/pnpm/Git | 缺失的是内置组件还是该功能的外部依赖 | 内置损坏引导应用完整性检查/更新；外部依赖仅在需要时指导安装 | 不让所有用户先装 Node、npm、Git；不默认管理员安装 |
| 无法写入 / 空间不足 | 错误路径、EACCES/EPERM/ENOSPC、可用空间 | 显示需要处理的位置；释放空间后重新检查，或进入可验证的迁移流程 | 不自动删除会话、备份或扩大权限；真实故障注入待验证 |
| 中文、空格、~/、外置盘路径出错 | 路径标准化、存在性、目录类型、权限 | 文件选择器保存绝对路径；仅展开明确的当前用户 ~/ | 不展开任意 shell 表达式或猜测其他用户目录 |
| 下载被认证/完整性策略拒绝 | 具体状态码、包源、校验结果 | 来源问题提供诊断摘要；校验失败停止并重新获取经验证的包 | 不建议关闭证书验证、绕过校验或盲目批准构建脚本 |
| 崩溃后某个会话打不开 | 该会话记录、尾记录或中间记录损坏 | 默认只读检查；可修尾记录另行保存原文件并暂停写入后修复 | 当前 doctor(true) 没有写入者互斥，不能直接自动化 |
| 迁移或恢复后原连接无法登录 | 缺失凭证清单、实际认证响应、是否换机器 | 保留非敏感连接配置，按连接逐项重新授权并复检 | 不承诺凭证可跨机器还原；不重复恢复整个工作区来修单个登录问题 |
| 安全模式能用，正常模式失败 | 已跳过的功能、版本证据、当前启动记录 | 临时继续工作，明确哪些功能不可用；下一步只针对有证据对象 | 安全模式仍可修改工作文件，不是只读沙箱 |
| 仍然无法确定原因 | 本次全部检查和已尝试动作 | 一键生成可预览的脱敏报告，用户选择复制或保存 | 默认不上传、不包含会话正文/密钥/完整环境变量 |

## 5. 收敛后的界面

### 统一入口

启动失败页、恢复页、设置中使用同一份故障状态与动作结果。设置入口叫“检查与修复”。商店、外部服务和模型失败保留在原功能旁，点击检查时带入失败目标；不强迫用户自己到设置里重找原因。

首屏一个主要动作，最多两个次要入口：技术详情、更多恢复方式。可用动作依据当前证据变化，不固定把所有模式和备份按钮排满页面。“恢复指定备份”保留在更多恢复方式中；打开后仍按时间倒序选择并确认。

推荐动作示例：

```text
启动还没有完成
已确认本地服务可响应，但工作界面未加载成功。
本次已重新连接 1 次，仍然失败。

[尝试安全模式]
使用原数据目录，临时跳过扩展功能；不会还原历史备份。

查看技术详情    更多恢复方式
```

```text
外部服务的文件夹找不到了
上次选择的位置现在无法访问。请确认磁盘已连接，或重新选择原文件夹。

[重新选择文件夹]    重新检查
```

只有检测结果足够明确时才显示对应具体原因；“插件不兼容”“磁盘空间不足”等标题不能从通用失败信息推断。

### 操作中与操作后

- 展示真实阶段：检查、准备、执行、验证。不要把无法测量的百分比伪装成进度。
- 同一故障的同一变更动作串行执行；重复点击、切页和重开窗口显示同一运行中的任务。
- 自动检查不改写业务数据；自动修复只使用已验证、范围固定的可逆规则。所有重试有上限并记录已尝试动作。
- 可取消的检查/下载显示取消；目录替换等不可中断步骤提前说明“正在完成数据切换”，不能显示虚假的取消按钮。
- 成功显示已恢复的能力；安全模式只能显示“安全模式已可用”，不能显示“原环境已修复”。
- 失败显示失败步骤、已完成内容、数据当前位置、下一步；保留原始证据，但详情和导出要脱敏。

### 模式与恢复范围

| 用户入口 | 真实影响 | 呈现规则 |
| --- | --- | --- |
| 尝试安全模式 | 使用原 DSH_HOME；跳过第三方插件、Skills、自定义模式和项目指令 | 主动选择；持续显示临时模式与退出入口；不能承诺全部功能仍可用 |
| 用临时空环境排查（隔离模式） | 使用临时 DSH_HOME，不加载原会话和凭证；退出或重新启用均会清理临时环境 | 高级选项；进入前说明原数据仍在、临时内容需要保留时应先导出 |
| 处理插件 | 根据当前 profile 和兼容性证据处理指定插件 | 停用与卸载分开；不称全部候选为“冲突插件” |
| 恢复指定备份 | 按 manifest 替换相应组件；旧备份没有 workflow 组件时仍会还原 state 中的工作流配置/记录，但保留独立工作流工作文件；不还原应用二进制 | 先显示日期、实际范围、缺失凭证、恢复前备份，再确认；不能暗示只改配置或只撤销一个插件 |

当前隔离模式只隔离 DSH_HOME，不隔离宿主机文件系统、启动目录或环境变量。`src/main/index.ts:427` 在任何模式 ready 时都会自动启动外部服务。因此在补充模式限制前，不能将它称作“排除所有外部影响”的检查环境。检查本身也不能隐式调用会修改 profile 的普通启动预处理；检查、修复和重试需要分别记录。

## 6. 分阶段交付

这些工作涉及不同生命周期，按可独立验证的子项目交付，不做一次性“大一键修复”。

| 顺序 | 可交付结果 | 主要文件 / 新模块边界 | 验收门槛 |
| --- | --- | --- | --- |
| 0（已实施） | 修正误导文案与已复现的安装归因 | `install-diagnostics.ts`、`locale.ts`、对应测试；[实施与验证记录](superpowers/plans/2026-09-13-environment-diagnostics.md) | 401/403 不判网络；一般 ENOENT 不判内置缺失；失败页不预设插件或升级原因 |
| 1A | 应用打不开时仍有恢复入口 | `index.ts` 启动编排、`workspace-service.ts` 指针读取、独立启动故障状态和最小 Renderer | 数据目录失败、损坏配置仍有可操作窗口；保留原数据位置，不静默回退默认目录 |

| 1C（首批已实施） | 目录与命令分别诊断，修正字段后保存并重试 | `external-service-manager.ts`、外部服务设置页；[实施记录](external-service-environment-recovery.md) | 本地反例和交互验证通过；Finder 与 Windows 发行启动路径仍待实测 |
| 2 | 同一故障只有一个推荐下一步 | 共享故障/检查结果类型、Main 检查任务、统一恢复面板 | 未知原因不猜测；去重、超时、取消和迟到事件测试通过；全程可查证据 |

## 7. 技术约束与失败反例

故障状态至少携带：本次 incidentId、启动/操作 attemptId、功能范围、失败阶段、当前证据、诊断确定性、已尝试动作、推荐动作及数据影响。检查结果分别为通过、失败、未知、未执行；任一必要项目未知时，不能显示“全部正常”。第一版使用现有 Main IPC 和类型，不引入独立后台服务。

| 反例 | 必须保持的行为 |
| --- | --- |
| 安装源 403，代理本身可连通 | 展示来源拒绝；不循环切代理、重装 Runtime |
| HTTP 200，但 Web 插件失败 | 保留事务和故障；不显示恢复完成 |
| 原因未知，但装了很多插件 | 列为排查候选；不随机停用/卸载 |
| 安全模式也失败 | 不连续切换模式掩盖原错误；保留报告并根据最新证据推荐下一步 |
| 旧检查结束时用户已经切换工作区 | 丢弃旧实例的结果与动作，不改动新工作区 |
| 磁盘满导致恢复前备份失败 | 不开始替换；保留当前数据和待恢复目标 |
| 还原前选择、摘要或归档目录预检失败 | 不停止仍工作的服务；展示失败并允许重新选择 |
| 同名归档在预检后被删改 | 真正恢复再次校验并拒绝不一致数据；承认服务可能已停，保留失败步骤 |
| 数据已还原，但 Runtime 启动失败 | 保留还原结果，只重试启动；设置页卸载不丢失当前操作反馈 |
| 还原过程中应用退出 | 重启后识别未完成阶段；验证实际目录与备份，不盲目继续或删除 |
| doctor 扫描后会话又写入 | 不用旧内容覆盖新文件；暂停写入并复核后再执行 |
| 隔离模式里用户创建了新内容 | 明确临时性与退出清理，不将其当作原环境恢复成功 |

代理统一覆盖需要逐路径核验，尤其是 Electron 网络、Node fetch、插件子进程和自定义外部服务。先明确网络配置作用域；不要默认覆盖外部服务自己的显式代理配置。本地 Runtime 始终保持 loopback 绕过。
