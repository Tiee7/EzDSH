# 恢复备份前先检查，启动失败只重试启动

2026-09-13，基线 `2a43a23`。本批落实环境恢复规划中“预检查失败不停止好应用”的首个片段。

## 用户得到的改进

恢复备份时，先检查选择是否能确定到一份完整名称的备份、校验归档摘要、读取归档目录；这些检查失败时直接显示错误，不先停止当前 Runtime 和其他服务，也不替换原有设置。用户可以重新选择备份。

设置页沿用一次恢复确认，使用当前界面语言说明备份名称和日期、会被替换的数据、恢复前另存当前状态，以及应用版本不会回退。需要重新补充的凭据按功能类别提示，不显示凭据内容。取消确认不执行真正还原，也不重启 Runtime。

恢复范围按备份 manifest 判断。包含 `workflow` 组件时会替换相应工作流工作文件；旧备份只包含 `harness` 和 `state` 时，会还原 `state` 中的工作流配置和运行记录，但保留独立 `workflow` 目录中的现有工作文件。确认信息分别说明这两种范围，不能将旧备份描述成“不会影响工作流”。

完成后显示“备份已还原，Runtime 已启动”，不再显示“备份已创建”。只有 Runtime 返回 ready 才显示启动成功。数据已经还原但 Runtime 启动失败时，提供“重试启动”：只重试 Runtime，不再还原一次备份。备份列表刷新失败也与数据还原失败分开说明。

还原过程中界面可能从设置页切到启动页或恢复页。进度、已经还原的结果和“重试启动”入口由 App 持有，设置页卸载后仍然保留；恢复页将提示放入可见卡片，设置页重新挂载时默认回到“备份与恢复”。用户尝试另一份备份但取消确认时，原来已还原结果的启动重试入口仍保留。

还原或重试尚未结束时，恢复页禁用其他恢复和模式切换入口。用户在启动失败后通过安全模式、隔离模式或其他启动入口成功进入 ready 时，清除此前的“尚未启动”提示和重试入口；本流程自己的启动仍保留成功信息。

## 实现顺序

`RecoveryRestoreCoordinator` 在任何异步工作开始之前登记恢复等待状态，按以下顺序执行：

1. Main 调用现有 `RecoveryManager.restore(selector, true)` 进行只读预检。
2. 保存预检返回的完整备份名称，避免停止服务期间新出现的同前缀备份改变选择。
3. 读取当前运行模式，停止应用组件。
4. 用确定的名称执行真正恢复；保留真正恢复时的再次校验。
5. 重新准备当前安全或隔离模式的专用资源，然后放行后续启动。

预检期间，第二个恢复请求会被拒绝；启动请求等待当前恢复结束。预检失败不调用停止、真正恢复或模式准备，等待中的启动收到失败；等待状态清理后可以重新选择并重试。

设置页自己的确认前预览仍保留。Main 在执行时再次预检，避免用户阅读确认信息期间备份已经变化，却直接停止当前环境。该检查增加一次摘要和目录读取；不缓存之前的预览来跳过执行时检查。

Renderer 的 `useRecoveryRestore` 由 App 创建，再传给设置页和恢复反馈组件。该流程以同步更新的当前操作状态阻止重复点击，验证 IPC 返回的结果类型和备份名称，再执行 Runtime 重启。真正还原成功后保留结果；启动重试只调用 Runtime，成功后再尝试刷新备份列表。列表刷新失败不会把已经完成的还原重新标成失败。

App 初次自动启动至多请求一次；恢复正在进行、还原结果等待启动重试或工作区正在切换时，不再发出自动启动请求与恢复争用。恢复后的启动由还原流程负责，用户仍可明确重试。

开始切换工作区时，App 清除还原提示和待重试结果，并使旧操作的后续回调失效。迟到的预览、还原或启动结果不会在新工作区显示旧提示，也不会触发旧流程的下一次 Runtime 重启。

## 已验证边界与后续事项

- 临时目录中的真实 RecoveryManager 与归档文件覆盖：空选择、缺失备份、损坏 manifest、摘要不匹配、摘要正确但归档无法读取。上述失败不调用停止组件，原设置和凭据字节不变，也不创建恢复前备份。
- 同前缀新备份在停止阶段出现时，仍恢复预检选中的完整名称。
- 预检完成后、停止前才捕获当前模式，避免把预检开始时的旧模式当作实际停止的模式；预检期间和停止回调同步触发的启动均须等待恢复完成。
- 模拟界面交互覆盖确认取消、预览/还原结果不符、Runtime 未 ready、启动重试、备份列表刷新失败、设置页卸载后继续反馈，以及切换工作区后忽略迟到结果。旧备份确认明确区分工作流配置/记录与独立工作文件。
- 预检之后同一归档被修改时，真正恢复仍拒绝校验失败，不替换原数据；这时服务可能已经停止。预检不能消除后续文件变动和操作系统错误。
- 现有 dry-run 只读取归档目录；解压后的必需组件、符号链接和磁盘写入条件仍在真正恢复期间检查。因此不能把“预检通过”写成“保证恢复成功”。
- App 持有的是当前 Renderer 生命周期内的状态，不是落盘恢复日志。重新加载窗口或退出应用后的恢复续接仍未实现；清除界面状态也不会撤销已经发给 Main 的还原操作，不能据此宣称支持恢复中断或跨工作区并发恢复。
- 本批覆盖普通备份恢复 IPC 和设置页流程；RecoveryPanel 的既有交互流程、插件回滚的独立停止/还原路径、完整服务实例重建仍需后续统一。Runtime 返回 ready 仅满足现有启动判断，不能证明所有业务能力、Web 插件和外部服务都已恢复；跨平台发行包验收仍待完成。
- 核查还发现 `latest` 在有多份普通备份时会报告选择不明确，以及 restore/verify 会重复读取 manifest。这些未纳入本批，不宣称已解决；后续应统一选择和校验输入，再考虑完整的预解压与恢复编排。

- Main、Renderer 两项类型检查与构建通过；构建保留既有 workflow-run-store 动态/静态混合导入提示。
- 本地浏览器使用真实恢复卡片和反馈组件、模拟还原状态，检查提示可见性与重试按钮点击；发现并修正深色启动页上的文字对比度。该预览不执行实际备份还原或 Runtime 启动。
- 独立审查提出的设置页卸载、反馈遮盖、恢复后默认页、重复自动启动和旧工作区迟到回调问题均已补上反例并通过。完整服务恢复、窗口重新加载后的续接和发行包验收仍不在本批完成范围。
