# 专业员工与工作流使用指南

EZDSH 的核心是工作流自动化。工作流定义一件事如何完成，专业员工负责其中需要稳定岗位能力的环节。

## 一、六个核心概念

```text
工作流 = 事情如何完成
专业员工 = 哪个岗位对专业环节负责
智能处理 = 当前流程中的轻量临时推理
技能 = 员工或节点可以调用的原子能力
任务 = 一次业务请求
运行 = 任务执行产生的技术记录
```

员工不是一条隐藏在岗位内部的小工作流，也不等于模型进程。它是一份可复用、可治理、可版本化的专业档案；流程顺序、分支、审批和跨岗位协作都由工作流负责。

## 二、何时使用智能处理，何时使用专业员工

使用“智能处理”节点：

- 临时总结、分类、改写或格式转换；
- 任务只在当前流程中出现，不需要稳定岗位身份；
- 不需要长期维护业务边界和质量责任；
- 可以选择单次处理或自主处理模式；
- 可以直接输出文本或 JSON，不必先创建员工。

使用“专业员工”节点：

- 同类工作会被多个工作流反复调用；
- 需要明确岗位职责和不得越过的业务边界；
- 需要固定执行规范、质量标准和技能集合；
- 需要知道结果由哪个岗位负责；
- 后续需要受控地评估和升级岗位能力。

例如，“把标题改短”适合智能处理；“审核短视频脚本的事实、品牌一致性和表达风险”适合内容审核员工。

## 三、专业员工档案

每个员工包含：

- 名称、角色和职责简介；
- 业务边界：负责什么、不负责什么；
- 工作原则与系统提示词；
- 执行规范：完成任务时应遵循的方法；
- 质量标准：交付结果的验收要求；
- 能力标签和可以调用的技能 ID；
- 档案版本、启用状态和内置标记。

设计员工时，先写清边界，再写方法和标准。避免“全能助手”一类无法验收的角色。好的边界示例：

> 负责检查短视频选题和脚本的钩子、逻辑、事实、品牌一致性与表达风险；不替代发布审批，也不自行发布内容。

执行规范应描述动作，例如“逐项检查事实主张并标记证据缺口”；质量标准应描述验收结果，例如“审核决定必须是通过、修改或人工处理之一”。

旧版员工数据在加载时自动迁移到档案 V2：原有员工步骤会成为非执行性的“执行规范”，不会继续形成员工内部工作流。每次修改员工档案都会增加档案版本。

## 四、工作流节点与 JSON 数据

工作流节点之间只交换 JSON-safe 数据：字符串、数字、布尔值、`null`、数组和对象。智能处理和专业员工节点支持两种输出格式：

- `text`：输出普通文本；
- `json`：输出结构化数据，供下游节点稳定读取。

当 JSON 首次解析失败时，运行时会在同一个 Session 中请求一次格式修复；第二次仍无效则节点失败，并留下明确错误。文件、图片和其他大对象后续应以 Artifact 引用传递，不应把二进制内容塞入节点 JSON。

工作流还支持 Input、Skill、MCP、Parallel、Loop、Condition、Approval、Transform、Output、Shell 和 File 节点。Shell/File 每次运行都需要显式授权，文件路径只能位于 Workflow 工作目录。

## 五、项目、Session 与一次性测试

工作流模板通过版本化 JSON 导入，页面不再内置“短视频内容运营”创建按钮。

```text
项目 = 任务所属的工作空间
Session = 一次模型工作的上下文
```

员工页的“测试员工”只用于拿一个真实任务验证档案配置，不代表员工拥有自己的工作流。同一个 Session 同时只能运行一个员工测试任务，避免上下文串线；不同 Session 可以并行测试同一员工。

正式的跨岗位工作应放入工作流运行。每次运行保存输入、节点状态、节点输出、错误和事件，可以取消、暂停、恢复，并在 Approval 节点等待人工决策。

## 六、当前边界

当前版本已经实现手动工作流运行、专业员工、智能处理、JSON 输出修复、运行记录和人工审批。工作流定义可以通过编辑器导出、在工作流列表导入版本化 JSON；业务模板应作为 JSON 文件或插件分发，不再由页面内置按钮写入项目。尚未实现：

- 定时触发、Webhook、邮件或 Git 事件；
- 持久任务队列和 24 小时后台 Worker；
- 工作流发布、不可变版本与回滚；
- JSON Schema 映射和 Artifact 管理；
- 预算、告警、重试/补偿和幂等策略；
- 员工长期记忆、候选经验、评估和自动升级；
- 外部平台自动发布；
- 使用 EZDSH 自动修改或升级 EZDSH 自身。

涉及事实、版权、平台规则、法律、医疗、财务或人事等高风险内容时，必须保留人工复核。专业员工的“能力”不等于它自动拥有外部系统权限。
