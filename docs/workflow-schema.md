# Workflow Schema v2

面向 AI 生成器的完整概念、决策规则和示例见 [AI 工作流生成规范](./ai-workflow-generation.md)。本文保留为 JSON schema 的快速参考；两者描述的运行语义必须保持一致。

AI workflow generation, persistence and the `workflow` field inside an import/export document use this JSON definition. The UI exchange envelope is documented in `docs/workflow-json.md`; a workflow is valid only when it satisfies the required fields and node rules below.

```json
{
  "schemaVersion": 2,
  "id": "workflow-company-analysis",
  "name": "企业分析",
  "description": "识别企业属性后生成对应分析报告。",
  "generationPrompt": "生成一个企业分析工作流",
  "revision": 1,
  "enabled": true,
  "createdAt": "2026-08-31T00:00:00.000Z",
  "updatedAt": "2026-08-31T00:00:00.000Z",
  "nodes": [
    {
      "id": "company-input",
      "type": "input",
      "label": "企业或产品名称",
      "config": { "name": "company" },
      "position": { "x": 80, "y": 180 }
    },
    {
      "id": "research",
      "type": "ai-task",
      "label": "企业识别与分析",
      "description": "先提取企业关键信息，再生成结构化分析。",
      "config": {
        "instruction": "请分析 {{company}}，只输出包含 summary 字段的 JSON 对象。",
        "mode": "single",
        "skillIds": [],
        "outputMode": "json",
        "outputSchema": { "type": "object", "properties": { "summary": { "type": "string" } }, "required": ["summary"] }
      },
      "inputBindings": [
        { "id": "research-company", "name": "company", "sourceNodeId": "company-input", "required": true }
      ],
      "outputVariables": [
        { "name": "summary", "description": "企业分析摘要" }
      ],
      "position": { "x": 344, "y": 180 }
    },
    {
      "id": "report-output",
      "type": "output",
      "label": "分析报告",
      "config": {},
      "inputBindings": [
        { "id": "output-summary", "name": "result", "sourceNodeId": "research", "sourcePath": "summary", "required": true }
      ],
      "position": { "x": 608, "y": 180 }
    }
  ],
  "edges": [
    { "id": "edge-company-research", "source": "company-input", "target": "research" },
    { "id": "edge-research-output", "source": "research", "target": "report-output" }
  ]
}
```

## Graph rules

- `nodes` use unique IDs containing letters, numbers, `.`, `_` or `-`; every node has `id`, `type`, `label`, `config` and numeric `position`.
- `nodes[].description` is optional editor context shown in the node inspector; it does not participate in execution.
- `generationPrompt` is optional metadata containing the original user prompt when the workflow was generated by AI; it is preserved through save, reload and export.
- `permissionPolicy.connectors` is an optional least-privilege declaration. Each entry names one connector and explicitly allows `read`, `write`, or both; managed HTTP runs require this declaration and a per-run grant that can only narrow it.
- A node may declare a bounded `retryPolicy` (`maxAttempts`, optional exponential backoff and jitter). Deterministic nodes may retry; managed HTTP writes may retry only with `mode: "idempotent"` and a remote API that honors `Idempotency-Key`. Raw external nodes are never blindly replayed.
- An effectful node may declare an explicit `compensation` action pointing to another Workflow. Compensation is manual and never inferred from the graph; uncertain external effects pause for reconciliation instead of being replayed.
- An `input` node may use `config.name` for one legacy/single-value input, or `config.fields` for multiple explicit launch parameters. Each field has `name`, optional `label`, `type` (`string`, `number`, `boolean`, `json`, `file` or `file-list`), `required` and `defaultValue`; downstream nodes select a field with `sourcePath`.
- `edges` use unique IDs and connect existing node IDs through `source` and `target`. They control execution order, branching and loops; they must not be empty for multi-node workflows, and must not form cycles.
- `inputBindings` is the only way a node receives data. Each binding has a local `name`, a `sourceNodeId`, an optional dot-separated `sourcePath`, and `required`. The node can use it in instructions as `{{name}}` or `{{name.field}}`; values not bound to the node are not interpolated.
- `sourcePath` omitted means the source node's complete `result`. For a JSON result, declare selectable fields in `outputVariables`; `result` is always implicit. A binding creates an execution dependency even if the nodes do not have a direct edge.
- The fixed `output` node also consumes `inputBindings`. With `config.contentMode: "variable"` (the default), one binding forwards its value and multiple bindings return an object keyed by their local names. With `config.contentMode: "text"`, `config.text` is a template; `{{name}}` and `{{name.field}}` are replaced from the output node's bound inputs, so several upstream values can be composed into one final string.
- `text-merge` is the convenient deterministic node for composing multiple text values. Bind each source with a local name, then set `config.template` such as `"标题：{{title}}\n正文：{{body}}"`; the node returns the rendered string. If the template is empty, bound values are joined in declaration order with `config.separator` (default newline).
- `transform` supports `text` in addition to `identity`, `json`, `extract-text`, `prepend`, `append` and `replace`. In `text` mode, `config.text` directly defines a new output string and can reference bound `{{variables}}`; it does not need to contain the original text. `replace` is reserved for literal find/replace on the first bound input and uses `config.find` / `config.replacement`, which also support variables.
- An `ai-task` with `outputMode: "json"` may declare `config.outputSchema`. The runtime validates the parsed result against this schema and retries once with a repair prompt when it does not match, so simple structured extraction does not need a separate node.
- `structured-extract` is the explicit extraction node for reusable extraction contracts: it accepts the bound input text, validates against `config.schema`, and retries up to `maxRetries` times. Use it when extraction itself should be visible as a distinct workflow step; use `ai-task.outputSchema` for a simple inline case.
- `object-builder` constructs nested JSON from constants, bound variables and `{{variable.path}}` templates (`config.fields`). `list-operator` provides deterministic `filter`, `map`, `pluck`, `sort`, `dedupe`, `slice`, `group` and `aggregate` operations; aggregation can count/sum/average/min/max a numeric field. `merge` combines multiple bound values with `append`, `object-merge`, `join`, `zip` or `first-non-null`.
- `sub-workflow` selects another saved workflow by `config.workflowId`, forwards the current input, waits by default, and returns the child output (or a child `runId` when `waitForCompletion` is false). `wait-input` currently supports the `approval` preset (同意/拒绝); legacy `approval` nodes remain readable for migration.
- A `sleep` node passes its input through unchanged. With `config.mode: "fixed"` (the default), it waits `config.durationMs`; with `config.mode: "random"`, each execution samples a new integer duration inclusively between `config.minDurationMs` and `config.maxDurationMs`.
- A node may bind multiple upstream nodes and one node may feed multiple downstream nodes. All edge and binding dependencies use AND semantics: the node waits until every dependency reaches a terminal state. There is no implicit any-one/OR/race merge; use `condition` for mutually exclusive paths.
- A `parallel` node runs several similar instructions inside one node and returns an array. It is not the same as graph fan-out, where one node has multiple visible downstream nodes. A `condition` has true/false exits; a `switch` has exact-value `switch:<caseId>` exits plus one `default` exit.
- The supported node types are `input`, `ai-task`, `structured-extract`, `employee`, `skill`, `mcp`, `parallel`, `loop`, `sleep`, `condition`, `switch`, `approval`, `wait-input`, `sub-workflow`, `object-builder`, `list-operator`, `merge`, `transform`, `text-merge`, `output`, `shell`, `file`, `http` and `code`.
- An `http` node with `connectorId`/`connectorPath` uses a main-process managed HTTPS connector, whose endpoint, path prefixes, credential scope, workflow policy and run grant are checked before dispatch; write requests receive a stable idempotency key. A node without those fields is a legacy raw HTTP request and is disabled by the production composition. Both forms return `{ status, ok, headers, body }` and fail on non-2xx responses.
- A `code` node runs Node.js or Python3 in a separate subprocess. Node.js code receives `input` and `previous` and returns a value; Python3 code receives the same variables and assigns `result`. Code execution is disabled unless the run dialog explicitly authorizes it, and every process has a timeout.
- A `file` node supports `read`, `write`, recursive directory `list`, `stat` metadata and text extraction for common text/HTML/JSON/PDF/RTF/DOCX files. Paths stay relative to the Workflow working root; DOCX extraction uses the host `unzip` utility when available.
- An `employee` node must use an existing, enabled employee ID and include a non-empty instruction. Employee catalog entries have a personal `displayName`, a formal `role`, and a legacy short `name`; use role/boundary/capabilities for matching, not the personal name. When no suitable employee exists, create one before graph generation; if creation is unavailable, use `ai-task`.
- A `condition` node uses exactly one of `truthy`, `equals`, `not-equals`, `contains`, `greater-than`, or `less-than`. Its outgoing branch edges use `sourcePort: "true"` or `sourcePort: "false"`. A `loop` node uses `sourcePort: "loop-body"` for the first node of a single linear downward body chain and `sourcePort: "loop-next"` for the single downstream continuation; every body-chain node runs once per input item, and the terminal body output is collected in order. Optional `concurrency` and `batchSize` fields are reserved for future scheduling; `failureStrategy: "continue"` records failed items and keeps iterating.
- A `switch` node declares one or more unique `{ id, value, label? }` entries in `config.cases`. Each case has exactly one outgoing edge with `sourcePort: "switch:<caseId>"`, and there is exactly one `sourcePort: "default"` edge. It forwards the matched input value unchanged; case IDs are used only for routing, and unmatched input follows the default edge.

Generated workflows are automatically laid out from this dependency graph before the editor opens. The editor also exposes **自动排版** to optimize any imported or manually edited document.

## P0 node configuration quick reference

The following snippets show the minimum configurations expected by the runtime. In every example, data still enters through explicit `inputBindings`; `{{value}}` and `{{input}}` are reserved template references for the current node input and original workflow input.

```json
{
  "type": "structured-extract",
  "config": {
    "schema": {
      "type": "object",
      "properties": { "title": { "type": "string" } },
      "required": ["title"],
      "additionalProperties": false
    },
    "maxRetries": 2
  }
}
```

```json
{
  "type": "sub-workflow",
  "config": {
    "workflowId": "clean-document",
    "waitForCompletion": true,
    "version": "latest",
    "inputMapping": { "document": "{{document}}" }
  }
}
```

```json
{
  "type": "object-builder",
  "config": { "fields": { "title": "{{title}}", "meta": { "source": "ezdsh" } } }
}
```

```json
{
  "type": "list-operator",
  "config": { "operation": "filter", "path": "status", "value": "ready" }
}
```

```json
{
  "type": "merge",
  "config": { "operation": "join", "leftKey": "id", "rightKey": "recordId" },
  "inputBindings": [
    { "id": "left", "name": "left", "sourceNodeId": "left-list", "required": true },
    { "id": "right", "name": "right", "sourceNodeId": "right-list", "required": true }
  ]
}
```

For human approval use `wait-input` with `mode: "approval"` and a non-empty `message`. The legacy `approval` type is read-only compatibility and should not be generated for new workflows.
