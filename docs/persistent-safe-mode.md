# 安全模式：继续使用与重启保留

2026-09-13，基于 `a93ad8f` 的改进。

## 用户行为

安全模式可以直接继续工作，无需先退出。它使用当前工作区原有的数据目录，保留会话、设置和凭据。修改模型等共享设置后仍保存到原位置；进入、退出安全模式都不是恢复默认设置。

安全模式只加载内置 Runtime 组件，暂停加载第三方插件、Skills、自定义 Agent 模式和项目指令。依赖这些扩展的功能需要用户主动选择“恢复扩展功能并正常启动”。正常模式仍按原配置加载，已禁用的插件不会因退出安全模式而全部启用。

| 操作 | 结果 |
| --- | --- |
| 在安全模式直接聊天、修改共享设置 | 继续使用原工作区；不要求退出 |
| 普通重启、代理设置触发重启、更新后重新启动 | 沿用当前 Runtime 的模式、数据目录和 profile |
| 关闭应用后重新打开工作区 | 读取该工作区记住的安全模式选择 |
| 上次插件故障仍待处理，重新打开工作区 | 已选择安全模式时自动继续；未选择时保留恢复页，不自动启动普通环境 |
| 切换到其他工作区 | 使用该工作区自己的选择 |
| 临时进入隔离模式 | 本次运行使用独立临时目录；不擦除原工作区记住的安全模式 |
| 隔离模式中普通重启 | 本次 Runtime 继续沿用隔离目录 |
| 关闭隔离模式中的应用后再打开 | 回到该工作区记住的安全模式；未记住时正常启动 |
| 明确退出恢复模式并正常启动 | 清理专用恢复资源、忘记安全模式选择，再正常启动 |
| 在安全或隔离模式恢复历史备份 | 恢复完成后重新准备当前模式的专用资源，再继续当前模式 |

隔离模式与安全模式不同：它不加载原环境的设置、凭据和会话，适合进一步排查，临时目录也不作为长期保存用户配置的位置。安全模式同样不是只读环境，用户和内置工具的正常文件修改仍会生效。

恢复页现有的插件回滚、停用或卸载并正常启动流程，也会明确恢复到正常模式。正常模式下还原包含历史安全模式选择的备份时，本次运行继续正常模式，下次重新打开工作区才读取历史选择。

## 实现与故障边界

- `SafeModeProfileController` 把选择独立保存到工作区 `state/safe-mode-selection.json`，内容为带版本的 safe 标记。它不存放模型、密钥或其他用户设置，也不放在会被重新生成的专用 profile 目录里。
- 冷启动读取时，只有标记确实不存在才按正常模式启动。损坏、未知版本和读取失败都会报告错误；不能因此静默加载原环境的插件。
- 启用成功后才保存选择；清理专用资源成功后才移除选择。专用 profile 和 preset 目录先在暂存位置完整生成再分别替换，安装失败尝试还原旧目录；不覆盖非 EzDSH 所有的同名资源。自动生成的 profile 不是用户设置编辑入口。两个目录不是跨目录事务，进程强杀可能留下暂存目录，但最终 profile 不发布半成品。
- `RuntimeManager` 首次无参启动在已有启动生命周期内解析选择。并发启动共享同一过程；停止后不得出现迟到启动；读取失败可以重试。显式上下文仍可用于用户选择的模式切换。
- App 的自动启动请求经过 Preload 传给 Main；有待处理恢复问题时，Main 禁止该次请求启动正常模式，但允许已经选择的安全模式。选择读取失败带独立来源标记，避免错误归因为尚未尝试的正常插件启动失败。手动正常启动行为保持明确可用。
- 后续无参 `start()` / `restart()` 保留完整上下文。Main 使用工作区局部 controller 闭包，避免切换工作区后读到其他工作区的选择。
- 临时隔离不移除安全模式选择。明确的正常启动恢复操作仍清理它。
- `RecoveryRestoreCoordinator` 在停止服务之前登记等待状态；备份恢复和专用资源准备全部成功后才放行启动。已等待的启动请求在任一步失败时一起失败，避免在替换目录期间提前启动。它仅补齐本次模式资源衔接，不声称解决已有的所有服务重建问题。
- 在安全或隔离模式修改插件后，自动重启保持当前模式，插件事务仍待正常模式验证。商店和已安装列表都明确提供“继续当前模式”与“正常启动并应用插件变更”，需要用户主动点击后者才切回正常模式；读取模式失败可以重新检查。受限环境启动成功不能证明正常插件配置可用；现有的待确认事务限制仍会阻止下一次插件变更。当前正常模式健康确认仍沿用原有 Runtime ready 判定，不等同插件实际能力验收。
