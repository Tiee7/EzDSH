# EZDSH 工作流中心化产品设计

**日期：** 2026-08-29

**状态：** 已完成产品讨论，等待书面规格确认

**定位：** 长期产品架构与对象边界

## 1. 背景

当前 EZDSH 同时提供“员工”和“工作流”两个功能，但两者都在描述完成工作的步骤：员工包含顺序执行步骤，工作流又提供独立的图形化编排。这会让用户无法判断应该先创建员工还是先创建工作流，也让两个功能形成没有价值的内部竞争。

本设计将 EZDSH 定位为工作流自动化平台。工作流是核心业务资产，员工是工作流可以调用的专业执行者，二者不再处于同一层级。

长期目标是让 EZDSH 能够在预先授权的边界内，定时、持续、无人值守地完成开发、运营、市场等知识工作，并逐步扩展到其他行业。近期首先验证日常内容运营，不包含 EZDSH 自我开发或自我更新。

## 2. 核心产品原则

1. 工作流回答“事情如何完成”，负责顺序、分支、并行、循环、审批、重试和补偿。
2. 员工回答“由谁负责”，负责业务边界、专业判断、技能、权限、质量和受控经验。
3. AI 处理负责轻量、临时的模型推理，不要求用户先创建员工。
4. 技能负责一个边界清晰的可复用能力，工具负责与外部系统交互。
5. 任务是业务请求，运行是工作流执行该请求产生的技术实例。
6. 节点之间默认交换带类型约束的 JSON；大内容、敏感数据和运行历史分别存储。
7. 自动化只能执行已发布的不可变工作流版本。
8. 无人值守代表在预先批准的边界内持续执行，不代表无限权限。

## 3. 产品对象模型

| 对象 | 职责 | 生命周期 | 是否长期复用 |
|---|---|---|---:|
| 项目 | 保存业务上下文、文件、代码、资料和约束 | 长期 | 是 |
| 工作流 | 定义完整业务过程 | 草稿、测试、发布、停用 | 是 |
| 工作流版本 | 固定节点、数据契约、引用和执行策略 | 发布后不可变 | 是 |
| 触发器 | 在时间或事件满足条件时创建任务 | 启用、暂停 | 是 |
| 任务 | 表达一次业务目标和输入 | 待处理到结束 | 否 |
| 运行 | 保存一次工作流执行状态和检查点 | 排队到终态 | 否 |
| 专业员工 | 可治理的专业岗位定义 | 草稿、验证、发布、升级 | 是 |
| AI 处理 | 当前工作流内的轻量模型任务 | 随工作流版本存在 | 通常否 |
| 技能 | 原子能力或可复用操作 | 版本化 | 是 |
| Artifact | 文档、图片、代码包等大内容 | 按保留策略管理 | 可复用 |
| 候选经验 | 从运行中提炼、尚未成为长期记忆的结论 | 待验证、接受、拒绝 | 否 |

### 3.1 专业员工

专业员工不是常驻进程，也不是增加了特殊提示词的普通模型调用。它是一个可复用、受约束、可审计的岗位定义，至少包含：

- 业务边界和拒绝范围；
- 专业指令和判断原则；
- 技能与工具组合；
- 项目、文件和外部系统权限；
- 输入输出契约；
- 质量标准和自检规则；
- 自主等级、预算和升级条件；
- 长期记忆策略；
- 版本和历史表现。

员工不再拥有与画布竞争的内部工作流。原有“员工工作流步骤”改为执行规范、质量清单或迁移成独立工作流。

### 3.2 AI 处理与底层 Agent

普通用户不需要理解 Agent 这一技术概念。产品层提供“AI 处理”节点：

- 默认模式是一次模型处理，适合摘要、分类、提取、改写和结构化输出；
- 高级模式为“自主执行”，允许在有限步骤、时间和预算内调用指定技能；
- 自主执行可以在底层使用临时 Agent 运行机制，但不具备跨任务长期身份和记忆；
- 当一个 AI 处理开始需要复用、独立权限、长期经验或质量责任时，用户可以将它保存为专业员工。

因此，大模型不必先包装成员工。模型是底层计算资源，AI 处理和员工都通过模型策略使用它。员工可以根据任务难度、成本、隐私或故障情况选择不同模型。

## 4. 工作流生命周期

标准生命周期为：

```text
草稿 → 测试 → 发布版本 → 启用触发器 → 持续运行
                  ↓
             暂停或回滚
```

规则如下：

- 草稿可编辑，但不影响已发布版本和正在运行的任务；
- 定时、Webhook 和事件触发器只能绑定已发布版本；
- 发布版本固定工作流结构、数据契约、员工版本、技能版本和执行策略；
- 正在运行的任务始终使用启动时快照；
- 新版本异常时可以将触发器切回旧版本；
- 员工和技能升级不会自动改变已发布工作流，必须显式升级引用；
- 凭证只保存引用，不进入工作流版本或运行输入输出。

## 5. 工作流数据模型

JSON 是 EZDSH 的通用数据交换语言，但不是唯一存储形式：

| 数据 | 处理方式 |
|---|---|
| 节点业务输入输出 | JSON，并使用 JSON Schema 验证 |
| 工作流和节点状态 | 持久化数据库与检查点 |
| 文档、图片、音视频、代码包 | Artifact 存储，JSON 只传引用 |
| 密钥、Token、账号凭证 | Secret Store，JSON 只传凭证引用 |
| 全量工具调用和运行历史 | 审计与可观测性存储 |

节点数据包采用统一信封，至少包含 `schema`、`data`、`artifacts` 和 `meta`。自然语言可以作为字段值存在，但条件分支、审批和自动统计不能依赖解析一整段自由文本。

每个节点需要声明输入和输出 Schema。数据选择采用受限路径表达式，数据转换采用无任意代码执行能力的映射表达式。大对象不进入工作流历史，敏感凭证不进入节点输入输出或日志。

## 6. 员工记忆

记忆按归属和作用域分层：

| 层级 | 内容 | 所属对象 |
|---|---|---|
| 运行记忆 | 当前输入、中间结果、节点状态和待审批事项 | 运行 |
| 会话记忆 | 当前任务中的对话和临时上下文 | 任务或 Session |
| 项目知识 | 业务资料、代码、历史决策和稳定约束 | 项目 |
| 员工经验 | 经过验证的偏好、案例、失败教训和专业规则 | 员工 |
| 审计历史 | 全量输入输出、工具调用、费用和异常 | 审计存储 |

运行结束后，员工只能生成带来源、作用域、置信度和有效期的候选经验。经过规则验证或人工确认后，候选经验才能成为长期记忆。原始运行历史不直接写入员工记忆，员工不能自行修改身份、权限和核心工作规范。

## 7. 自主权与安全

自主能力分为观察、受监督执行、有界自动执行和完全自动运行。实际权限为以下范围的交集：

```text
用户授权 ∩ 项目权限 ∩ 工作流权限 ∩ 员工权限 ∩ 节点权限
```

默认策略：

- 读取、分析和生成草稿可以自动执行；
- 内部且可逆的写操作可以在明确边界内自动执行；
- 外部发布、部署、合并代码或发送消息默认需要审批，可在发布时明确授权；
- 删除、付款、生产权限修改等高风险操作必须采用更严格授权；
- 员工不得自行扩大权限或绕过审批；
- 所有自动运行都有时间、调用次数、费用和并发预算；
- 系统提供全局暂停、触发器暂停和运行取消能力。

## 8. 运行架构

目标架构采用设计控制端与执行端分离的混合模式：

```text
桌面端或未来 Web 控制台
→ 控制服务
→ 持久化任务队列
→ 本地、私有或未来云端 Worker
→ AI 处理、员工、技能、脚本和外部系统
```

- Renderer 只负责设计和展示，不能承载实际执行；
- 控制服务负责版本、触发器、授权、调度和运行状态；
- Worker 使用租约和心跳领取任务，异常后任务可以恢复；
- 本地 Worker 适合访问本机文件和代码；真正的 24 小时运行需要始终在线的机器或未来云端 Worker；
- 初期可以继续使用本地数据库和单机队列，但接口不得依赖 Electron 页面生命周期；
- 当前开发继续沿用项目现有方式；EZDSH 自我开发和自我更新不属于本设计范围。

## 9. 用户工作方式与信息架构

标准用户旅程：

```text
准备资源 → 设计工作流 → 配置执行者 → 测试 → 发布
→ 自动运行 → 监控和审批 → 复盘学习 → 发布新版本
```

建议一级功能：

| 功能 | 定位 |
|---|---|
| 控制中心 | 运行状态、异常、审批、费用和今日成果 |
| 工作流 | 设计、测试、发布和管理自动化 |
| 员工 | 管理专业岗位、权限、技能和经验 |
| 技能与连接 | 管理原子能力、外部系统和凭证 |
| 项目与知识 | 管理文件、代码、业务资料和上下文 |
| 模板 | 复用行业工作流、员工和能力组合 |
| 设置 | 模型、预算、安全和系统配置 |

Workbench 重新定位为临时任务台。一次性工作在任务台完成；重复出现的任务可以转为工作流草稿；重复出现的专业角色可以保存为员工；重复出现的操作可以提取为技能。

## 10. 失败处理与测试

失败分为暂时性故障、契约错误、质量不通过、权限或凭证错误、Worker 中断、预算超限、外部副作用状态不确定和永久配置错误。分别采用有限重试、结构化修复、返工回路、暂停等待、租约恢复、停止执行、状态核对和人工处理。

关键规则：

- 每个节点保存输入、输出、尝试次数和检查点；
- 从失败节点恢复，不无条件从头重跑；
- 写操作需要幂等键或重复执行保护；
- 重试、循环和返工都有上限；
- 外部结果不确定时先核对状态，禁止盲目重试；
- 无法自动恢复的任务进入“需要处理”队列。

测试分为节点测试、Schema 契约测试、草稿工作流测试、外部系统沙箱测试和历史数据回放测试。高风险工作流按照草稿、沙箱、人工真实运行、小范围定时运行、完全无人值守的顺序逐级开放。

## 11. 分阶段实施

| 阶段 | 范围 | 验收目标 |
|---|---|---|
| 1 | 重构工作流、员工、AI 处理、技能、任务和运行的边界 | 员工与工作流不再竞争 |
| 2 | 用短视频选题和文案流程验证手动端到端执行 | 可以稳定生成可审批内容 |
| 3 | JSON 契约、测试、发布、定时触发、持久化队列和运行中心 | 可以每天无人值守交付内容 |
| 4 | 权限、预算、重试、告警和更多外部连接 | 可以安全运行更多业务及外部项目开发 |
| 5 | 分层记忆、候选经验、评估和员工版本升级 | 员工可以受控积累经验 |
| 后续评估 | 扩展到更多行业、私有或云端 Worker | 按真实需求独立立项 |

EZDSH 自我开发不属于当前阶段。只有前五阶段完成、多个 Release 版本稳定运行后，才重新评估该方向，并单独立项设计和授权。

## 12. 兼容和迁移

- 现有工作流定义和运行记录尽可能保持可读；新增 Schema 版本负责迁移；
- 现有 `agent` 节点迁移为 AI 处理节点，并根据配置保留自主执行能力；
- 新增独立的专业员工节点，引用固定员工版本；
- 现有员工的角色、提示词和能力继续保留；
- 现有员工内部步骤不再作为员工长期能力继续扩展，可转换为执行规范或独立工作流草稿；
- 迁移前保留原始数据，不进行不可逆覆盖；
- 当前员工和工作流功能在迁移期间保持可用，避免一次性破坏已有用户数据。

## 13. 当前明确不做

- EZDSH 修改、提交、合并或发布自身代码；
- EZDSH 自动更新自身；
- 默认自动发布短视频或向外部平台发送内容；
- 让员工无审核地修改核心提示词、权限或长期记忆；
- 在工作流定义中执行任意 JavaScript；
- 将大文件或密钥直接放入节点 JSON。
